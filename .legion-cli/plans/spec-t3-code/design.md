## Functional and user-experience design

Create a named instance in the selected environment through existing web/desktop settings/onboarding or the new mobile provider-instance settings route. Choose Token Plan with explicit China/Singapore/Europe account region or supported custom Chat Completions endpoint. Enter a credential with explicit model IDs; validate against qualified metadata before save. Use typed secret annotations and masked presence with explicit replace/clear, never a round-tripped plaintext value. Saving confirms configuration only. Runtime/model availability depends on supported runtime and coding capability checks. Actual live verification requires an explicitly initiated evidenced run and is invalidated when its configuration changes; no new global status store is necessary merely to convey these distinctions.

Pick the stable instance/model through the existing catalog, run normal coding/tool/approval/checkpoint flows, and reconnect to the same saved thread from another authorized client. Edit while idle; active disruptive mutation gets a server rejection with wait/explicit-cancel guidance. Cancellation requested is still busy until actual work settles. Disable has re-enable. Removal preserves thread history and an unavailable reference, never a reassignment. Missing CLI/version, auth, quota, region/model and network errors identify the next user action without raw causes or credentials.

## Architecture and interfaces

Use packages/provider-mimo with browser-safe settings/client metadata and isolated server exports. Existing ProviderDriver, ProviderAdapterV2, ProviderInstanceMutation, server.updateSettings, createEnvironmentRpcCommand, provider catalogs and ServerSecretStore carry the feature. Contracts never import provider packages. Maintain existing wire shapes unless qualification proves a required change; such a change needs a reviewed contract increment. Persisted existing provider events/config remain decodable, unknown/unavailable instances remain visible, and independently upgraded clients retain negotiated capability behavior.

MiMo is a distinct driver with its own qualified release and configuration policy. User-managed destination-host CLI only; no separate OpenCode install, automatic external server reconfiguration, new OAuth flow or agent loop. Default to independent protocol implementation; only demonstrated compatible exported utilities may be reused. No OpenCode source refactor is assumed. Keep credentials in the environment secret store and materialize only at the owning runtime boundary. Instance IDs key runtime state; thread/session IDs isolate T3 MCP/permissions. Durable session state survives safe process rebuilds; temporary process configuration has explicit protected cleanup.

All disruptive entrypoints converge on the server service boundary. ServerSettingsService already serializes settings writes and rolls back secret changes, but its duplicate-create guard does not protect work. Registry hydration closes changed instance scopes asynchronously. Introduce only the coordination needed to make admission, accepted mutation and targeted reconciliation mutually ordered. Reserve before command commit (including queued promotion/delegated/scheduled paths); retain through pending/active/background work; release on authoritative settlement/start failure. Reconstruct reservations after restart before allowing mutations. Preserve pure decisions and outbox side-effect ordering. Declare consistent instance/thread/settings lock order and do not await termination under a lock termination needs.

When admission wins, reject mutation before any settings/secret write. When mutation wins, do not admit into an old runtime generation; finish owning-instance reconciliation or expose unavailable state first. Cancellation requests do not bypass this. Preserve another instance's scope/catalog. A failed rebuild cannot silently change credentials/provider/billing route. These boundaries belong to one server task because splitting shared ownership would permit inconsistent partial integration.

## Compatibility, quality attributes and failures

Existing Codex managed setup, Claude, Cursor, Grok, OpenCode (including external servers), Antigravity and other registered drivers retain their existing behavior. They do not acquire MiMo version or billing policies. No database migration or stored-thread rewrite is planned. No always-repainting UI, background coding/login, remote discovery requirement, global catalog refresh or full-thread streaming expansion. Keep status payloads bounded and changes scoped by instance. Preserve current checkpoint, approval, sandbox and remote authorization behavior.

Client required scopes mirror destination authorization for provider mutations and mixed generic patches; do not weaken settings permissions to make the form work. Secrets cannot appear in UI, exports, logs, process diagnostics or evidence. Server authorization is authoritative even when UI guards disable a control. Two same-named instances in separate environments cannot alias.

## Infrastructure, installation and recovery

No new cloud service, deployment, tunnel configuration, runtime distribution, native module or automatic installer is required. Existing destination host, T3 state and secret store remain the operational boundary. Package/workspace registration is grouped in TSK-0003; exact release/endpoint metadata enters only after qualification. Runtime support targets Windows/macOS/Linux; local Windows results are not cross-platform qualification.

The maintainer reviews/approves the plan and executes offline work; the environment operator installs the qualified CLI and supplies secrets using product controls. The account owner separately authorizes live calls/billing. The primary integrator performs any authorized client/device pass; an independent reviewer assesses the consequential server change. Recovery settles/cancels work before disabling the affected instance, preserves saved threads and state, and repairs configuration before re-enabling. A release/rollback cannot retire required evidence or mutate live/global state. New version support requires requalification; no silent OpenCode-derived compatibility fallback.

## Verification design

TSK-0002 runs an isolated real-CLI probe against loopback model fixtures before any product task. Backend additions use test-first behavior through service/adapter boundaries; an actual reproduced regression uses regression-first in its existing suite. Existing tests protect unchanged providers. UI logic uses meaningful unit/native interactions; no static-markup assertions or invented browser gate in automated commands. Deterministic races await Deferred/Queue/persisted events or effect-worker drain, never sleeps, time deltas or retry.

Each named command on the board executes once at its owning task; C-TYPES runs once after integration. Check outcomes are distinct from manual/client, live provider, platform and review evidence.
