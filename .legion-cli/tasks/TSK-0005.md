# Enforce atomic instance mutation, secret ownership and work settlement on the server

Acceptance: AC-P0-02, AC-P0-03, AC-P0-04, AC-P0-05, AC-P1-01, AC-P1-03, AC-P1-06, AC-P1-07, AC-P1-09, AC-CH-01.

FileContract: only contract.filesAllowed may be changed; other source files are read-only. Preserve WIP and task ownership. No approval, commit or publishing is implied.

Planned command identities: C-SETTINGS, C-LIFECYCLE, C-ORCHESTRATION.

## Observable result

Register the distinct driver and typed secret fields in existing environment-owned settings/secret infrastructure. Stable instance identity scopes storage, redaction, credential materialization, catalog refresh, continuation and runtime ownership. Reuse existing secret rollback/removal handling; do not change ServerSecretStore implementation or write live userdata. Verify its existing persistence guarantees through tests and the integrated fixture.

Before any disruptive MiMo config/credential/disable/remove write, use one service-level instance lifecycle boundary shared by settings mutation and work admission. Prefer extending existing service machinery; the allowed ProviderInstanceLifecycle module is for the missing cross-service coordination only. Account for pending committed starts, active turns, queued promotion, delegated/scheduled work and still-running background children. A cancellation request, returned startTurn or provider completion before remaining affected runtime work settles must not release the guard prematurely.

Serialize admission/reservation with settings mutation before command commit, including message.dispatch and internal startNextQueuedRun callers. Keep pure command/event decisions free of provider/filesystem I/O; perform coordination in the service execution boundary. Retain the reservation through authoritative terminal/start-failure/child-settlement transitions. On restart, reconstruct pending/active reservations from durable work and recovered runtime state before reopening mutations; fail closed when recovery cannot establish settlement. Never add a competing scheduler or polling loop.

Apply the same checks to ProviderInstanceMutation and generic settings patch entrypoints (and reject any alternate override path that could mutate the instance). Check permission and validation before writing secrets. A rejected active-work mutation leaves both secrets and saved settings unchanged. Serialize the accepted write, owning-instance reconciliation and catalog invalidation before reopening admission. Hydration must not independently close an active scope or race a replacement. Never hold the settings semaphore while waiting for cancellation or an event that needs it; define one lock ordering that respects existing thread/parent-child locks.

On validation/persistence/rebuild failure, either preserve the old coherent generation or expose the saved new configuration as unavailable without admitting work into stale configuration. Do not silently roll back to a different credential/account/billing route. Keep the original error category redacted. Rename-only handling can avoid rebuild if proven safe; disruptive changes must always reject while busy.

Disable has re-enable; removal keeps saved threads/history and an explicit unavailable provider reference. Re-enable must recheck prerequisites. Preserve stable continuation identity across permitted rebuilds; no silent reassignment after removal, disabled state, restart or failed resume. Existing Codex managed credentials and externally hosted OpenCode behavior remain unchanged.

## Verification

C-SETTINGS tests through ServerSettingsService and destination RPC authorization: two instance secret records, replace/clear/removal, rollback, generic patch bypass, denied/wrong destination and absence from projected/exported state. Existing ServerSecretStore regression runs without editing its implementation.

C-LIFECYCLE establishes race order deterministically with Deferred/Queue: admission wins => mutation rejects before writes; mutation wins => new admission observes fully reconciled generation; queued/committed-not-started work counts; cancellation requested but unsettled rejects; terminal plus child settlement permits; hydration/rebuild failure does not corrupt the other instance. Test startup recovery and lock-order cases without sleeps/time deltas.

C-ORCHESTRATION covers streaming/session continuity, queued/delegated and scheduled entry paths sharing admission, permissions/approval, cancel completion, restart recovery, preserved history and checkpoints. Extend the narrow existing suites owned here and drain OrchestrationEffectWorkerV2 or await persisted events. No giant suite run or timeout/retry exemptions. The final two-instance full-stack scenario belongs to TSK-0008.

## Ownership and recovery limit

This is deliberately one consequential task: settings, hydration and orchestration files cannot be safely owned by independent writers. It must be independently reviewed. Do not partly enable driver registration while leaving any mutation/admission path unguarded. If implementation needs EventSink, ProjectionStore, transport, migration or additional files, report extra work for a reviewed contract amendment rather than expanding this list.
